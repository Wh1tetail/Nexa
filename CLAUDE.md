# NEXA LMS — notes for Claude

Online English school LMS. Russian UI by default (English supported). Full docs: `README.md`.

## Layout
- `backend/` — FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL. Layers: `core/` (settings, db, security), `models/`, `schemas/` (Pydantic, server-side validation), `repositories/`, `services/` (business logic), `api/v1/endpoints/`, `storage/`, `middleware/`.
- `frontend/` — React 18 + TS + Vite + Tailwind + shadcn-style components (`src/components/ui`), TanStack Query, react-hook-form + Zod.

## Commands (Windows, Git Bash)
- Database: local PostgreSQL 18 Windows service (`postgresql-x64-18`, port 5432); main DB from `DATABASE_URL` in `backend/.env`, tests use `<db>_test`. Fallback without an install: `cd backend && .venv/Scripts/python -m scripts.dev_postgres` (port 4934)
- DB inspection: `postgres-dev` MCP server, read-only role `nexa_readonly`, URL in `NEXA_RO_DATABASE_URL` (`.claude/settings.local.json`, not in git)
- Migrations: `cd backend && .venv/Scripts/alembic upgrade head`
- Backend: `cd backend && .venv/Scripts/python -m uvicorn app.main:app --port 8000` (or the `backend` entry in `.claude/launch.json`)
- Frontend: `cd frontend && npm run dev` (Vite proxies `/api` to :8000)
- Tests (real PostgreSQL, ~10 min; wipe the `<db>_test` database each run): `cd backend && .venv/Scripts/python -m pytest -q`. Only one run at a time: the `single_pytest.py` hook blocks a pytest command while another pytest process is alive (wait for the running one)
- Lint: `cd backend && .venv/Scripts/python -m pyflakes app tests scripts`
- Dependencies: `backend/requirements.txt` = runtime only (goes into the Docker image); dev/CI tools in `requirements-dev.txt`
- CI: `.github/workflows/ci.yml` (backend tests on PostgreSQL 18, frontend build, docker compose smoke test). Production: `docker-compose.yml` + `.env` from `.env.production.example`. Docker is not installed locally — the compose stack is verified only in CI.
- Types/build: `cd frontend && npx tsc -b --noEmit` / `npm run build`
- Demo data: `cd backend && .venv/Scripts/python -m scripts.seed --reset` (password `Demo12345` for all demo users)
- Production server (README «Запуск на VPS с доменом»): `docker compose --profile https up -d --build` (Caddy HTTPS for `DOMAIN`, nginx bound to `HTTP_BIND=127.0.0.1`); first admin `python -m scripts.create_admin`, SMTP check `python -m scripts.send_test_email`; the `backup` service writes DB dumps + file archives to `BACKUP_DIR`. New backend settings must also be passed through `docker-compose.yml` and listed in `.env.production.example`.

## Rules that are easy to break
- Ownership: teacher endpoints load students/groups/lessons via `get_owned_*` in `app/api/deps.py`; foreign objects return **404**, not 403. Students only ever see their own data.
- Creating students, groups and lessons (and deleting groups/lessons, extending series) is admin-only: use `AdminForTeacher`; reading/editing uses `ActingTeacher` (teacher = own data, admin = teacher from `X-Teacher-Id`/`?teacher_id=`). Teachers may only change a lesson's topic, add students and mark attendance. Subscriptions: teachers only view them; create/edit/extend/use-lesson/freeze/delete are `AdminForTeacher` (frontend: `useCanManageSubscriptions`).
- Deleting users (`DELETE /admin/users/{id}`) relies on DB cascades: `subscriptions.teacher_id` is ON DELETE CASCADE, so a teacher's students AND subscriptions must be moved first (`_hand_over_students` in `endpoints/admin.py`). Delete users with a core `delete(User)` statement, not `db.delete(user)` (the ORM would try to null the profiles' FKs).
- Student lessons/homework/tests/attendance (and their files) require an active subscription: use `StudentWithAccess`, not `CurrentStudent` (403 `code: "subscription_required"`); checked live, so renewal reopens access.
- Every API change touches four places: Pydantic schema → `frontend/src/types/api.ts` → `frontend/src/services/api.ts` → a test in `backend/tests/`.
- Server texts (errors, ValueError, notifications) are Russian templates translated via `app/core/i18n.py` CATALOG: pass values as params (`BadRequest("Не более {n} файлов", n=5)`, `M(...)` for notifications) — never f-strings; a test fails if a text has no kk/en translation. E-mail templates take the recipient's `lang`.
- Every UI string goes into `frontend/src/i18n/ru.ts`, `en.ts` and `kk.ts` (the `Dict` type enforces matching keys). Kazakh dates are built in `utils/format.ts` (`formatInstant`) — browsers often lack Kazakh month names.
- Schema changes go through an Alembic migration (see the `create-migration` skill); never edit applied migrations.
- E-mail is sent only through `services/email_service.py`: from requests via `BackgroundTasks`; copies of notifications/chat messages only via the outbox worker (`services/email_outbox.py`) — never send those from a request.
- Bumping `users.token_version` revokes all sessions and closes open SSE streams (`services/realtime.py`). Other live events go through `realtime.publish(db, ...)` inside the transaction (delivered on commit), e.g. chat in `services/message_service.py`.
- Participation is soft-removed (`removed_at` on `attendance`, `test_assignments`, `homework_submissions`): never delete these rows to take a student off — use `services/participation.py` (it also refunds/re-charges lessons and keeps group lessons in step). `Lesson.attendance` and `Test.students` hold active rows only; raw queries on these tables must filter `removed_at IS NULL` for anything the student or the statistics see.
- Test attempts: a student may have several per test (`TestAttempt.number`); the latest is `attempts_of(...)[-1]`, the best (`best_attempt`) counts in analytics. Never delete attempts to allow a retake — add `test_assignments.extra_attempts`.
- Test question types live in `services/task_types.py` (`config` JSONB): `fill_gaps`, `matching`, and content blocks `audio` / `reading` (`CONTENT_TYPES`, 0 points, no answers, questions after a block belong to it). Never send answers in `config` unless revealed — go through `public_config`. Any new server text in `TaskError` needs kk/en too.
- Library tests are `Test(is_library=True, teacher_id=None)`, managed only through `/library` endpoints (`LibraryEditor` = methodist/admin, `LibraryReader` adds teachers, who see published ones only). Teacher test endpoints must keep filtering by `teacher_id`, so library tests never leak there. A teacher uses one via `copy_test` (independent copy, files duplicated in storage) — never link a library test to students directly. Methodists have no students, groups or lessons.
- Courses (`models/course.py`): Course → CourseLevel → CourseModule → CourseLesson → LessonBlock. Block settings live in `LessonBlock.content` (validated by `services/lesson_blocks.normalize`); exercise blocks keep `content["questions"]` in the test `QuestionIn` format and are graded with `test_service.auto_grade` — never send them unrevealed except through `lesson_blocks.view_questions`. Lesson files are `Attachment.course_lesson_id`; copies duplicate them (`file_service.duplicate_attachment`). Editors = `LibraryEditor`; teachers (`LibraryReader`) get 404 for unpublished courses/lessons. Saving a lesson keeps the ids of blocks sent back with their id (future progress refers to them).
- Course assignments (`services/course_progress.py`): a level or a module per assignment (`group_id` = follows the group via `participation.change_group_members`); members and assignments are soft-removed (`removed_at`). Students reach lessons only through `lesson_access` (active, started assignment, published course and lesson, `StudentWithAccess`). `LessonProgress` is the history: never delete it — it survives lesson deletion (`lesson_id` NULL); `complete_lesson` locks the row and is idempotent (XP must hang off it, not off requests). Assigned courses/levels/modules can't be deleted (`assert_not_assigned`).
- XP and achievements (`services/gamification.py`): award only through `_award` / `_grant` (unique key + `ON CONFLICT DO NOTHING`) from confirmed events — `on_lesson_completed` (after `complete_lesson` returns True) and `on_test_graded` (every time an attempt becomes graded; repeats pay nothing). Never sum XP from anything but `xp_transactions`; point values come from `get_settings` (admin-editable `app_settings`). Learning days (`mark_activity`) use the student's time zone.
- Book-to-Test books (`models/book.py`, `services/book_service.py`, `endpoints/books.py`): `LibraryEditor` only (methodist UI, admin through the same right); the PDF is an `Attachment` with `book_id` (never a separate store, or the orphan sweep deletes it), saved with `Storage.save_file` (streamed, never read into memory). Limits come from `BOOK_MAX_UPLOAD_MB` / `BOOK_MAX_PAGES` (nginx has a 210m `location = /api/v1/books`).
- Book-to-Test jobs: long work (PDF processing, AI) runs only in the worker (`python -m app.worker`, compose service `worker`) through `services/book_jobs.py` — `enqueue` in the request, handlers registered in `services/book_processing.py` with `@register(kind)`; never run it inside a request. Handlers raise `FinalJobError` / `RetryableJobError` with a code, report through `JobContext.progress` / `check_cancel`, and never put book text into errors or logs.
- Book-to-Test text: pages and chapters are written only by the `extract` job (`services/pdf_extract.py` reads, `book_processing.extract` stores, in one transaction). Chapters a methodist created or edited are `origin = manual`: if any exist, reprocessing keeps all chapters and refreshes only page texts. Chapter edits go through `book_service._check` (range inside the book and the parent, depth <= 3, no cycles). OCR only through `services/ocr_service.py` (engine registry, `OCR_ENABLED`/`OCR_ENGINE`); the parser never renders pages itself.
- AI (Book-to-Test): only `services/ai_client.py` talks to a provider (transport + tested retry/model-switch policy, `AIUsage` tokens and estimated cost); model ids and keys come from settings (`AI_MODEL`, `AI_FALLBACK_MODELS`, `ANTHROPIC_API_KEY`), never from business code; no beta fallback parameters. Every generated question goes through `QuestionIn` (`services/question_generator.py`) and stays a draft until a methodist approves it. Review (`book_service.review`) re-checks every draft on the server (`QuestionIn` + `draft_warnings`; `source_not_found` blocks approval); editing a draft sends it back to review; exported drafts are frozen. Export (`services/draft_export.py`) takes approved drafts only into an unpublished library test, never publishes. `test_questions.source` (book, pages, quote) is editors-only: `question_out` returns it only with `with_source=True` (test editor, library detail) — never pass that on a student path; the frontend editor must carry `source` through load/save. Lesson exercises keep `source` inside `content["questions"]` (editors get raw questions; `lesson_blocks._q` never passes it to students). Never log the key or book text; tests use a fake transport, never the real API.
- Chat threads are keyed by `student_id` and exist only between a student and their CURRENT teacher; anything else is 404.
- Time: store UTC; anything "wall clock" (weekly series, texts for people, CSV) goes through `app/core/timezones.py` with the user's `users.timezone`. Frontend formats only via `utils/format.ts` (profile time zone), never raw `toLocaleString`/`setHours`.
- Main data lives in PostgreSQL; `localStorage` only holds the refresh token and UI preferences.
- No horizontal scroll at 375px; dialogs are bottom sheets on mobile.
- Light and dark themes: colours only through the tokens in `src/index.css` (`bg-card`, `text-primary`, `text-success-strong`, `bg-brand`, `text-accent-foreground`…), never hex/`hsl()` literals or `text-white` on `bg-accent`; a fixed palette needs `dark:` variants (see `components/ui/avatar.tsx`).
- Never edit `backend/.env` (use `.env.example`) or lock files by hand — a hook blocks it.
