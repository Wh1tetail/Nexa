# NEXA — LMS для онлайн-школы английского

[![CI](https://github.com/Wh1tetail/Nexa/actions/workflows/ci.yml/badge.svg)](https://github.com/Wh1tetail/Nexa/actions/workflows/ci.yml)

Полноценная платформа: публичный сайт, авторизация, кабинеты **ученика** и **преподавателя**, домашние задания с файлами, тесты с автопроверкой, посещаемость, абонементы и уведомления. Все данные хранятся в PostgreSQL.

```
frontend/   React 18 + TypeScript + Vite + Tailwind + shadcn/ui (Radix) + TanStack Query + RHF + Zod
backend/    FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL + JWT
```

## Быстрый старт

### 1. База данных

Нужен PostgreSQL 14+ (основной вариант для разработки — установленный PostgreSQL 18 как служба Windows на порту 5432). Создайте две базы — основную и тестовую с суффиксом `_test`:

```sql
CREATE DATABASE english_lms;
CREATE DATABASE english_lms_test;   -- для автотестов
```

Имена могут быть любыми: тесты берут базу `<имя из DATABASE_URL>_test` (например, `Nexa` → `Nexa_test`) или адрес из `TEST_DATABASE_URL`. Тестовая база **полностью очищается** при каждом запуске, поэтому она обязана отличаться от основной — `conftest.py` это проверяет.

**MCP-доступ к базе только на чтение** (сервер `postgres-dev` в `.mcp.json`): создайте роль `nexa_readonly` с паролем и правами только на `SELECT`, а её адрес положите в `.claude/settings.local.json` (файл не попадает в git):

```json
{ "env": { "NEXA_RO_DATABASE_URL": "postgresql://nexa_readonly:ПАРОЛЬ@127.0.0.1:5432/english_lms" } }
```

`.mcp.json` подставляет его как `${NEXA_RO_DATABASE_URL}`, поэтому пароль не хранится в репозитории.

Нет установленного PostgreSQL? Для разработки можно поднять локальный сервер без установки (пакет `pgserver` с бинарниками PostgreSQL 16) — после создания `.venv` из шага 2:

```bash
cd backend && .venv/Scripts/python -m pip install pgserver && .venv/Scripts/python -m scripts.dev_postgres
```

Скрипт создаст обе базы и напечатает готовую строку `DATABASE_URL`.

## Архитектура

### Backend (`backend/app`)

| Слой | Назначение |
|---|---|
| `core/` | настройки (`pydantic-settings`, всё из `.env`), подключение к БД, JWT/bcrypt, исключения |
| `models/` | SQLAlchemy-модели (14 сущностей + связующие таблицы) |
| `schemas/` | Pydantic-схемы запросов/ответов — серверная валидация |
| `repositories/` | переиспользуемые запросы (поиск/фильтрация учеников) |
| `services/` | бизнес-логика: статусы абонементов, списание занятий, проверка тестов, уведомления, файлы |
| `api/v1/endpoints/` | REST-роутеры; `api/deps.py` — текущий пользователь, проверка ролей и принадлежности |
| `storage/` | `LocalStorage` (dev) и `S3Storage` (любое S3-совместимое хранилище) |
| `middleware/` | заголовки безопасности, ограничение попыток входа |
| `alembic/` | миграции |

### Схема БД

`users` → `student_profiles` / `teacher_profiles` (1:1). Ученик принадлежит преподавателю (`student_profiles.teacher_id`).
`groups` + `group_students` (M:N). `subscriptions` (CHECK: даты, `0 ≤ used ≤ total`).
`lessons` → `attendance` (уникально `lesson_id+student_id`, `charged_subscription_id` для отката списания).
`homework` → `homework_submissions` (по одной на ученика, уникально) → `attachments` (CHECK: ровно один владелец).
`tests` → `test_questions` (варианты и правильные ответы в JSONB), `test_assignments` (M:N), `test_attempts` (одна попытка на ученика) → `test_answers`.
`notifications` (индекс `user_id, is_read, created_at`), `password_reset_tokens` (хранится только SHA-256 токена).

Перечисления хранятся как VARCHAR + CHECK (проще мигрировать, чем нативные enum).

### Ключевые правила

- **Статус абонемента** вычисляется, а не хранится: `frozen` → `expired` (дата окончания прошла) → `expiring_soon` (≤ 7 дней) → `active`. Цвет прогресс-бара: зелёный / оранжевый / красный.
- **Списание занятий**: отметка «Присутствовал»/«Опоздал» списывает занятие с действующего абонемента; смена на «Отсутствовал»/«Уважительная» или удаление занятия — возвращает. Можно и вручную («Списать/Вернуть занятие»).
- **Заморозка**: при разморозке дата окончания сдвигается на срок заморозки.
- **Уведомления об окончании**: фоновая задача (раз в час) уведомляет преподавателя и ученика о скором окончании/окончании абонемента — без дублей.
- **Тесты**: закрытые вопросы проверяются автоматически; короткий ответ — автоматически при совпадении с эталоном (без учёта регистра), иначе вручную. Таймер контролируется и на клиенте (автоотправка), и на сервере. После начала прохождения вопросы блокируются от изменений.

### Безопасность

- bcrypt (12 раундов) с SHA-256 pre-hash; пароли: ≥ 8 символов, буквы и цифры (проверка на клиенте и сервере).
- JWT access (30 мин) + refresh (14 дней); `token_version` в БД — выход из аккаунта и смена пароля отзывают все токены.
- Роли проверяются зависимостями FastAPI; чужие сущности возвращают 404 (не раскрываем их существование).
- Ученик видит только свои данные; преподаватель — только своих учеников, группы, задания, тесты, файлы.
- Файлы: белый список расширений, лимит размера (по умолчанию 10 МБ, потоковое чтение), проверка содержимого по magic bytes (`filetype`), случайные имена в хранилище, защита от path traversal, скачивание только через API с проверкой прав.
- SQL — только через ORM/параметризованные запросы. Ограничение попыток входа и восстановления пароля (общее для всех процессов, в PostgreSQL). Секреты — только в `.env`.

### Frontend (`frontend/src`)

`components/ui` — дизайн-система в стиле shadcn/ui; `components/*` — доменные компоненты; `pages/{public,auth,student,teacher,shared}`; `layouts/` (адаптивный сайдбар → выдвижное меню на мобильных); `services/` (axios-клиент с авто-refresh токена, типизированный API); `contexts/` (Auth, I18n); `i18n/` — словари `ru` (по умолчанию) и `en`, тип словаря гарантирует, что все ключи переведены. Страницы кабинетов загружаются лениво (code splitting). Skeleton-загрузчики, toast-уведомления (sonner), подтверждения для удаления.

## Этап 3 — уведомления в реальном времени

Уведомление появляется у пользователя сразу после события: всплывающее сообщение с кнопкой «Открыть», новая запись вверху центра уведомлений, обновлённый счётчик. Связанные данные тоже обновляются сами — например, у ученика сразу появляется новое ДЗ в списке.

```
notify() -> INSERT notifications -> after_flush: pg_notify('nexa_notifications', json)
          -> COMMIT (событие уходит только при успешном коммите)
PostgreSQL --LISTEN--> поток-слушатель в каждом процессе backend
          -> NotificationBroker -> открытые SSE-потоки этого пользователя
GET /api/v1/notifications/stream (text/event-stream, Authorization: Bearer)
          -> фронтенд читает поток через fetch (токен не попадает в URL)
```

- **Шина событий — сам PostgreSQL (`LISTEN/NOTIFY`)**, поэтому доставка работает при нескольких воркерах или серверах без Redis. При откате транзакции событие не уходит (покрыто тестом).
- **Код:** `app/services/realtime.py` (хук публикации, брокер, слушатель с автопереподключением) и `app/api/v1/endpoints/notifications.py` (SSE-эндпоинт).
- **События потока:** `ready`, `notification`, `expired`, плюс служебный `ping` каждые 15 с. Поток закрывается, когда истекает access-токен, — клиент обновляет токен и переподключается.
- **Клиент** (`src/services/realtime.ts`, `hooks/useNotifications.ts`):
  - переподключается с нарастающей паузой (backoff);
  - watchdog: если 40 с не приходит ни данных, ни `ping`, соединение пересоздаётся;
  - на странице уведомлений есть индикатор «В реальном времени» / «Переподключение…».
- **Опрос API остаётся запасным вариантом:** раз в 30 с, пока поток недоступен, и раз в 5 мин, пока он работает.
- **Найдено и исправлено при проверке:** после перезапуска backend прокси Vite держал «мёртвое» соединение открытым, и клиент перестал получать события. Watchdog решает эту проблему (проверено вручную: переподключение через ~23 с, доставка возобновилась).
- **Продакшен:** за nginx для `/api/v1/notifications/stream` нужно отключить буферизацию (`proxy_buffering off;`, backend и так шлёт `X-Accel-Buffering: no`) и задать `proxy_read_timeout` больше 15 с.

## Этап 4 — редактирование серий занятий

- **«Применить изменения»** при редактировании занятия из серии: «Только к этому занятию» или «К этому и следующим (N)».
  - Изменяются только **запланированные** занятия серии после выбранного. Проведённые и отменённые не трогаются, поэтому история посещаемости сохраняется.
  - **Новое время применяется как сдвиг.** Например, 18:00 → 19:30 переносит все следующие занятия на +1:30, а дни недели сохраняются.
  - Отправляются **только изменённые поля**. Если поменять одну тему, время и участники остальных занятий не перезапишутся.
  - Состав участников меняется во всех затронутых занятиях. Ученика с уже отмеченной посещаемостью убрать нельзя.
- **«Отменить это и следующие»** — отмена хвоста серии. «Вернуть в расписание» восстанавливает одно занятие.
- **«Продлить серию» / «Сделать повторяющимся»** добавляет N недель после последнего занятия серии с теми же участниками. Одиночное занятие так превращается в серию.
- На карточке занятия показан номер в серии: «3 из 8».
- Ученики получают **одно сводное уведомление** («Занятия изменены: «Club»: 3 занятий начиная с …») вместо уведомления на каждое занятие. Добавленные в серию ученики тоже его получают.
- API:
  - `PATCH /lessons/{id}?scope=one|following`;
  - `POST /lessons/{id}/series/extend {weeks}`;
  - в `LessonOut` добавлены поля `series_position` и `series_total`.
- Миграция не нужна: используется поле `series_id` из миграции `0002`.

## Этап 5 — закрытие потоков при завершении сеанса

Когда сеанс пользователя отзывается, его открытые потоки уведомлений закрываются сразу, а не по истечении токена. Сеанс отзывается при выходе, смене или сбросе пароля, задании пароля администратором и деактивации — во всех этих случаях увеличивается `users.token_version`.

- **Backend.** Хук `after_flush` замечает изменение `token_version` и публикует в тот же канал PostgreSQL событие `{"user_id", "revoke": <новая версия>}`. Как и уведомление, оно уходит только при успешном коммите и доходит до всех процессов backend.
  - Каждый поток знает версию своего токена. Если пришла более новая версия, поток отправляет событие `revoked` и закрывается.
  - Поток, открытый уже с новым токеном, не трогается.
- **Frontend.** Получив `revoked`, клиент перепроверяет сеанс:
  - **токен ещё действителен** (например, пароль сменили в этой же вкладке и она получила новые токены) — клиент сразу переподключается;
  - **иначе** пользователь выходит из аккаунта с сообщением «Сеанс завершён: выполнен выход из аккаунта, изменён пароль или доступ отключён».
  - Во вкладке, где нажали «Выйти», ложного сообщения «Сессия истекла» нет.
- **Вкладки одного браузера** используют один общий вход (refresh-токен в `localStorage`):
  - выход в одной вкладке завершает сеанс и в остальных;
  - смена пароля в одной вкладке оставляет остальные вкладки этого браузера в системе;
  - другие устройства со смены пароля отключаются.
- **Тесты** (на настоящем uvicorn-сервере):
  - выход закрывает поток;
  - смена пароля закрывает старый поток, а новый продолжает получать уведомления;
  - деактивация администратором закрывает поток ученика, не затрагивая поток другого ученика.

## Этап 6 — часовые пояса и календарь

- **Часовой пояс пользователя** (`users.timezone`, миграция `0003`, имена IANA вроде `Europe/Moscow`):
  - при первом входе подставляется пояс браузера;
  - менять его можно в «Настройках»: популярные российские пояса идут первыми, есть кнопка «Определить автоматически»;
  - пока пояс не выбран, сервер использует `DEFAULT_TIMEZONE` (по умолчанию `Europe/Moscow`).
- **Все даты и время в интерфейсе** показываются в поясе профиля, а не браузера (`frontend/src/utils/format.ts`). Поля ввода даты и времени тоже работают в этом поясе. Даты без времени (сроки абонементов) никогда не «съезжают» на соседний день.
- **Серии занятий** строятся по местному времени преподавателя (`backend/app/core/timezones.py`):
  - «каждый понедельник в 18:00» остаётся 18:00 и после перехода на летнее или зимнее время;
  - так же работают продление серии и сдвиг «это и следующие» (19:30 местного у всех занятий серии).
- **Уведомления об изменении занятий** приходят с временем в поясе каждого ученика, например «10.01.2027 18:00 (Asia/Yekaterinburg)», а не в UTC.
- **Экспорт посещаемости в CSV** использует пояс преподавателя (он указан в заголовке столбца).
- **Календарь занятий:**
  - у преподавателя — вкладка «Календарь» на странице «Расписание и посещаемость»: недели листаются, клик по занятию открывает отметку посещаемости (если занятие уже началось) или редактирование;
  - у ученика — раздел «Расписание» с цветом по отметке посещаемости и ссылкой «Подключиться»;
  - на телефоне вместо 7 колонок — список по дням.
- Новая зависимость `tzdata`: на Windows нет встроенной базы часовых поясов.
- Тесты (`tests/test_timezones.py`) проверяют реальный переход Европы на летнее время 28.03.2027: в UTC занятия сдвигаются на час, а по местному времени остаются в 18:00.

Разное:
- **Зависимости разделены:** `backend/requirements.txt` — только то, что нужно для работы (идёт в образ), `requirements-dev.txt` — плюс тесты и линтер.

## Этап 8 — сообщения между преподавателем и учеником

**Чат.** Пункт «Сообщения» в меню преподавателя и ученика, со счётчиком непрочитанных.
- **Преподаватель** (`/teacher/messages`, `/teacher/messages/:studentId`):
  - список всех своих учеников: сначала диалоги с новыми сообщениями, есть поиск по имени;
  - на телефоне сначала список, затем диалог с кнопкой «назад».
- **Ученик** (`/student/messages`) видит один диалог — со своим преподавателем.
- **В диалоге:**
  - разделители по дням с учётом часового пояса профиля, отметки «отправлено» и «прочитано»;
  - кнопка «Показать более ранние» (по 50 сообщений);
  - Enter отправляет, Shift+Enter — новая строка; не больше 4000 символов.
- **Доставка в реальном времени** — через тот же SSE-поток, событие `chat`:
  - у получателя сразу обновляются диалог и счётчики, а если диалог не открыт, появляется всплывающее уведомление;
  - отправитель видит отметку «прочитано», как только собеседник открыл диалог.
- **Правила доступа:**
  - писать можно только в пару «ученик — его текущий преподаватель»;
  - чужие диалоги возвращают 404, админ получает 403;
  - после перевода ученика к другому преподавателю прежний теряет доступ к переписке;
  - деактивированному пользователю написать нельзя (400), но история остаётся видна.

```
GET  /api/v1/messages/threads                       список диалогов (+ последнее сообщение, непрочитанные)
GET  /api/v1/messages/unread-count                  сколько непрочитанных всего
GET  /api/v1/messages/threads/{student_id}?before_id=&limit=   история (новые 50, затем более ранние)
POST /api/v1/messages/threads/{student_id}          {"body": "..."} → 201
POST /api/v1/messages/threads/{student_id}/read     отметить прочитанными сообщения собеседника
```

Миграция `0004`:
- таблица `messages`: индекс по диалогу и частичный индекс по непрочитанным, CHECK на длину;
- таблица `auth_attempts`.

**Ограничитель попыток входа теперь в PostgreSQL.**
- **Общий лимит.** Лимит в 10 попыток за 15 минут (на e-mail, отдельно для входа и для восстановления пароля) действует для всех процессов и серверов. Раньше он хранился в памяти каждого процесса.
- **Попытка засчитывается всегда.** Она пишется отдельным соединением, поэтому откат запроса с ошибкой 401 её не отменяет.
- **Без e-mail в базе.** Ключи хранятся как SHA-256.
- **Таблица не растёт.** Устаревшие записи удаляются при следующей попытке.

**CI.** Действия GitHub обновлены до `actions/checkout@v7`, `setup-python@v7` и `setup-node@v7` (Node 24). Предупреждение об устаревшем Node 20 больше не появляется.

Тесты:
- `tests/test_messages.py`: обмен сообщениями, счётчики, прочтение, 404 для чужих диалогов, валидация, постраничная история, перевод ученика, деактивация, доставка событий `chat` через живой SSE-поток;
- `tests/test_ops.py`: общий лимит между «процессами», истечение окна, хеширование ключей.

## Этап 9 — файлы в чате и уведомления на e-mail

**Файлы в чате.** Кнопка-скрепка в диалоге позволяет прикрепить до 5 файлов к одному сообщению.
- Подпись необязательна: сообщение может состоять только из файлов.
- Правила те же, что у файлов домашних заданий: белый список форматов, лимит размера, проверка содержимого по magic bytes, случайные имена в хранилище.
- Все файлы проверяются до сохранения: если хотя бы один отклонён, не сохраняется ничего.
- Скачать файл чата могут только двое участников диалога. Администратор и другие пользователи получают 404, а после перевода ученика к другому преподавателю прежний теряет доступ и к файлам.
- В списке диалогов и во всплывающих уведомлениях сообщение из одних файлов показывается как «📎 имя файла».

```
POST /api/v1/messages/threads/{student_id}/files   multipart: files (1–5) + body (необязательно) → 201
```

**Уведомления на e-mail.** Письмо приходит только о том, что осталось непрочитанным в NEXA дольше `EMAIL_NOTIFY_DELAY_MINUTES` (по умолчанию 10 минут). Кто сидит в приложении, писем не получает.
- **Одно письмо на получателя.** Все накопившиеся события собираются в одну сводку. Для чата это «Преподаватель: 2 — «последнее сообщение»», со ссылкой сразу в нужный диалог.
- **Настройки.** В «Настройках» появилась карточка «Уведомления на e-mail» с пятью переключателями: сообщения, домашние задания, тесты, занятия, абонемент. По умолчанию всё включено. Сохраняется в `users.email_prefs` через `PATCH /api/v1/auth/me`; можно передать только часть категорий.
- **Как устроено.** Письма отправляются не из запросов, а фоновым обработчиком очереди (`app/services/email_outbox.py`, запускается из `app/main.py` раз в `EMAIL_OUTBOX_INTERVAL_SECONDS`):
  - строки уведомлений и сообщений помечаются полем `email_processed_at`;
  - при нескольких процессах работает только один (advisory-блокировка PostgreSQL);
  - строки помечаются и фиксируются в базе до отправки, поэтому письмо может потеряться при сбое, но никогда не уйдёт дважды.
- **При обновлении писем не будет.** Миграция `0005` помечает все уже существующие уведомления и сообщения как обработанные, чтобы при выкатке не пришла лавина старых писем.
- **Отключение.** `EMAIL_NOTIFICATIONS_ENABLED=false` выключает рассылку целиком.

Тесты (`tests/test_chat_files_email.py`):
- файлы в сообщении и права на скачивание;
- лимиты, атомарность при отклонённом файле;
- письмо приходит один раз и не раньше задержки;
- прочитанное вовремя и выключенные категории не отправляются;
- проверка настроек;
- сводка по чату с файлами.

## Этап 10 — казахский язык, счётчики в меню, настройки и файлы тестов

**Казахский язык** (`frontend/src/i18n/kk.ts`).
- Третий язык интерфейса наряду с русским и английским. Переключатели: «Русский / Қазақша / English» в «Настройках», «RU / ҚАЗ / EN» на главной странице.
- Выбор сохраняется в профиле (`users.locale = "kk"`).
- **Даты по-казахски собираются в коде**, например «14 қар. 2026 ж.», «сб, 14 қар.», «кеше». Многие браузеры, в том числе встроенный ICU Chrome, не содержат казахских названий месяцев и показывают «M11 14».
- **Часовые пояса Казахстана** (Алматы, Костанай, Кызылорда, Актобе, Актау, Атырау, Уральск) добавлены в группу популярных.
- **Тексты вне словарей.** Ошибки проверки файлов и сообщения о потере связи тоже перенесены в словари.

**Счётчики новых уведомлений в боковом меню.**
- У пунктов «Домашние задания», «Тесты», «Расписание» и «Абонемент(ы)» показано число непрочитанных уведомлений этого раздела. У «Сообщений» — непрочитанные сообщения, как и раньше.
- Когда пользователь открывает раздел, его уведомления считаются просмотренными, и счётчик (вместе с колокольчиком) уменьшается.
- Счётчики обновляются в реальном времени через тот же поток событий.

```
GET  /api/v1/notifications/unread-by-section   → {"homework": 1, "tests": 2, "lessons": 0, "subscription": 0}
POST /api/v1/notifications/read-section        {"section": "tests"} → {"count": 2}
```

**Тесты: файлы и настройки.**
- **Материалы теста.** Преподаватель прикрепляет к тесту до 20 файлов: тексты для чтения, аудио для аудирования, картинки. Проверки те же, что у файлов домашних заданий.
  - Любой файл можно показать в конкретном вопросе: картинки и аудио отображаются прямо в вопросе, остальные файлы — для скачивания. Файлы, не привязанные к вопросам, идут блоком «Материалы» над вопросами.
  - Ученик получает доступ к файлам только после начала теста, чтобы не было подглядывания в аудирование. Другим ученикам и преподавателям — 404.
  - После начала теста материалы, как и вопросы, менять нельзя.
- **Настройки теста** (их можно менять и после начала прохождения):
  - «Открыть тест» — до этого времени тест начать нельзя, в списке видно «Откроется …»;
  - проходной балл в процентах — ученик и преподаватель видят «Зачёт» или «Незачёт»;
  - перемешивание вопросов и вариантов ответов. Порядок свой у каждой попытки и не меняется при перезагрузке; преподаватель видит исходный порядок;
  - «Показывать правильные ответы» — если выключено, ученик после проверки видит баллы, но не правильные ответы и пояснения.
- **Пояснение к вопросу** — ученик видит его вместе с результатом.
- **Пересдача.** Кнопка «Разрешить пересдачу» в результатах теста удаляет попытку, а ученик получает уведомление, что тест можно пройти ещё раз.

```
POST   /api/v1/tests/{id}/files                 multipart files → 201
DELETE /api/v1/tests/{id}/files/{file_id}       (вопросы перестают на него ссылаться)
POST   /api/v1/tests/attempts/{attempt_id}/reset
```

Миграция `0006`:
- поля настроек в `tests`, `explanation` и `attachment_ids` в `test_questions`;
- `attachments.test_id`, четвёртый владелец в CHECK.

Тесты (`tests/test_stage10.py`):
- счётчики по разделам;
- материалы и доступ к ним;
- отвязка удалённого файла;
- дата открытия;
- стабильное перемешивание;
- проходной балл и скрытые ответы;
- пояснения;
- пересдача;
- блокировка вопросов при изменяемых настройках;
- локаль `kk`.

## Этап 11 — сервер говорит на языке пользователя, чистка хранилища

**Ответы сервера на языке интерфейса** (`app/core/i18n.py`).
- **Передача языка.** Фронтенд отправляет язык интерфейса в заголовке `Accept-Language`. По нему переводятся:
  - ошибки API;
  - сообщения проверки форм (свои и стандартные из Pydantic, которые раньше приходили по-английски даже в русском интерфейсе);
  - ответы вроде «Приглашение отправлено на …»;
  - заголовки и статусы в CSV посещаемости.
- **Каталог сообщений.** Ключ — русский текст (как в gettext), значения — казахский и английский. Сообщения с числами и именами передаются шаблоном с параметрами: `BadRequest("Не более {n} файлов", n=5)`. Если перевода нет, ответ будет на русском, а не ошибкой.
- **Уведомления и письма — на языке получателя** (`users.locale`), а не того, кто действие совершил: преподаватель работает по-русски, ученик с казахским интерфейсом получит «Жаңа үй тапсырмасы». Названия заданий, имена и другой пользовательский текст не переводятся. Письма (восстановление пароля, приглашение, сводки) написаны на трёх языках.
- **Язык нового пользователя.** Он наследует язык того, кто его создал (преподавателя или администратора); на этом языке приходит и приглашение. Потом язык можно сменить в настройках.
- **Проверка полноты каталога.** Тест `test_every_server_text_has_kazakh_and_english` разбирает код и падает, если у нового текста ошибки или уведомления нет перевода или параметры в переводе не совпадают.

**Чистка хранилища от «осиротевших» файлов** (`app/services/storage_cleanup.py`).
- **Откуда они берутся.** При каскадном удалении (ученика, теста, задания, сообщения) строки файлов исчезают из базы, а сами файлы оставались в хранилище.
- **Как чистится.**
  - Раз в `STORAGE_SWEEP_INTERVAL_HOURS` (по умолчанию 24, 0 — выключить) backend сравнивает хранилище с таблицей `attachments` и удаляет файлы без записи.
  - Берутся только файлы старше `STORAGE_SWEEP_GRACE_HOURS`, чтобы не задеть только что загруженный файл, запись о котором ещё не сохранена.
  - Работает и для локального хранилища, и для S3.
  - При нескольких процессах чистит только один (advisory-блокировка).
- **Ручной запуск:**

```bash
cd backend && .venv/Scripts/python -m scripts.sweep_storage --dry-run
```

Тесты (`tests/test_server_i18n.py`):
- ошибки на трёх языках, в том числе с параметрами и без шаблона (ограничитель входа);
- стандартные и свои сообщения проверки;
- уведомления на языке получателя;
- письма на языке получателя;
- язык нового пользователя;
- CSV;
- полнота каталога;
- чистка хранилища: старый осиротевший файл удаляется, свежий и используемый остаются.

## Этап 12 — успеваемость и аналитика

**«Аналитика» у преподавателя** (`/teacher/analytics`).
- **Сводка по ученикам.** Число учеников, средний балл за тесты и за домашние задания, посещаемость.
- **Фильтры:** период (30, 90 дней или год) и группа.
- **Таблица учеников:**
  - средние баллы и посещаемость с полосой-индикатором;
  - число просроченных ДЗ, последняя активность, причины для внимания.
  - Сверху идут ученики, которым нужно внимание; имя ведёт в профиль.
- **Причины для внимания:**
  - посещаемость ниже 70% (при 3 и более отметках);
  - средний балл за тесты ниже 60%;
  - 2 и больше просроченных ДЗ;
  - закончившийся абонемент;
  - нет активности 14 дней: ни входов, ни сданных работ, ни тестов.

**«Мой прогресс» у ученика** (`/student/progress`) и **вкладка «Прогресс» в профиле ученика** у преподавателя.
- **Карточки:**
  - средний балл за тесты с трендом: последние 3 теста против 3 предыдущих;
  - средний балл за ДЗ;
  - посещаемость;
  - доля ДЗ, сданных вовремя.
- **Графики:** баллы за тесты, баллы за ДЗ, посещаемость по месяцам за полгода. Месяцы считаются в часовом поясе того, кто смотрит.
- **Как сделаны графики.** На своём SVG, без библиотек.
  - В каждом графике одна серия, поэтому смысл не зависит от различения цветов.
  - При наведении (и с клавиатуры) показываются подробности.
  - У каждого графика есть табличный вид.
  - Разбивка посещаемости (был, опоздал, не был, уважительная) — в подсказке и таблице. Статусные цвета, выстроенные стопкой, не прошли проверку на различимость при дальтонизме, поэтому от них отказались.

```
GET /api/v1/analytics/overview?period=90&group_id=   (преподаватель; period 7–365 дней)
GET /api/v1/analytics/students/{student_id}         (преподаватель, только свои ученики — иначе 404)
GET /api/v1/analytics/me                            (ученик)
```

Тесты (`tests/test_analytics.py`):
- прогресс ученика (средние, «вовремя», зачёт, помесячная посещаемость);
- права доступа;
- причины для внимания и порядок строк;
- фильтры по группе и периоду, неактивные ученики.

## Доступ по абонементу и права администратора

**Абонемент открывает занятия, домашние задания и тесты.** Ученик видит их только при действующем абонементе: он уже начался и не истёк и не заморожен (статусы «активен» и «скоро истекает»). Без абонемента, после окончания, во время заморозки или до даты начала:
- сервер отвечает `403` с `{"detail": ..., "code": "subscription_required"}` на `/me/homework*`, `/me/tests*`, `/me/attendance` и на скачивание файлов заданий/тестов;
- панель ученика показывает предупреждение и не показывает занятия/задания; `GET /auth/me` и `/dashboard/student` возвращают `access_active: false`;
- разделы «Расписание», «Домашние задания», «Тесты», «Посещаемость» отмечены замком и показывают экран с кнопками «Мой абонемент» и «Написать преподавателю».

Проверка выполняется при каждом запросе (`subscription_service.has_access`), поэтому после продления или разморозки всё открывается сразу, без повторного входа (фронтенд перепроверяет доступ при возврате на вкладку). Абонемент, профиль, сообщения и уведомления доступны всегда.

**Учеников, группы и занятия создаёт только администратор.**

| Действие | Преподаватель | Администратор |
|---|---|---|
| Создать ученика, группу, занятие/серию; продлить серию; удалить группу или занятие; отменить занятие | — | ✓ |
| Изменить существующего ученика или группу (состав, название) | ✓ | ✓ |
| Занятие: сменить тему, добавить существующих учеников, отметить посещаемость | ✓ | ✓ |
| Занятие: время, название, ссылка, статус, убрать учеников | — | ✓ |
| Абонементы: просмотр | ✓ | ✓ |
| Абонементы: оформить, изменить, продлить, списать/вернуть занятие, заморозить, удалить | — | ✓ |

Администратор работает с данными конкретного преподавателя: в разделах «Группы», «Расписание» и «Абонементы» (`/admin/groups`, `/admin/lessons`, `/admin/subscriptions`) сначала выбирается преподаватель, после чего фронтенд отправляет заголовок `X-Teacher-Id` (или `?teacher_id=`). Без выбора сервер отвечает `400 «Выберите преподавателя»`. В бэкенде это зависимости `ActingTeacher` (преподаватель — свои данные, администратор — выбранный преподаватель) и `AdminForTeacher` (только администратор).

Списание занятий при отметке посещаемости остаётся автоматическим — преподаватель по-прежнему отмечает присутствие.

Тесты: `tests/test_access_rules.py`.

## Этап 13 — несколько попыток теста и история результатов

Раньше у теста была одна попытка, а «пересдача» удаляла прежний результат. Теперь попытки нумеруются и сохраняются.

- **Настройка теста «Количество попыток»** (1–10, по умолчанию 1 — как раньше). Засчитывается **лучший** результат: он идёт в аналитику и показывается на карточке теста («лучший результат»).
- **Ученик** видит на карточке «Попытка 1 из 3» и кнопку «Пройти ещё раз», пока попытки остались и срок не прошёл. На странице результата — список «Мои попытки» со ссылками на каждую.
- **«Разрешить ещё попытку»** у преподавателя больше ничего не удаляет: ученик получает одну дополнительную попытку сверх настройки теста (`test_assignments.extra_attempts`), и её можно использовать даже после срока сдачи.
- В результатах теста у преподавателя видны все попытки с номерами.
- Незавершённая попытка бывает только одна (частичный уникальный индекс): повторное открытие или двойной клик продолжает её, а не создаёт новую.

Миграция `0007` безопасна для действующих данных: все существующие попытки получают номер 1, у существующих тестов остаётся одна попытка.

API:

```
POST /api/v1/me/tests/{test_id}/start?retake=true   (ученик: следующая попытка; без retake — продолжить/открыть последнюю)
GET  /api/v1/me/tests/{test_id}/attempts            (ученик: мои попытки, новые сверху)
POST /api/v1/tests/attempts/{attempt_id}/retake     (преподаватель: +1 попытка ученику; заменил /reset)
```

`StudentTestItem` получил `attempts_used`, `attempts_allowed`, `can_retake`, `best_percent`; `AttemptSummary` — `number`; настройки теста — `max_attempts`. Тесты: `tests/test_attempt_history.py`.

## Запуск на VPS с доменом

Нужен **VPS** (виртуальный сервер) на Ubuntu 22.04/24.04 с доступом по SSH: обычный «shared»-хостинг для сайтов на PHP/WordPress не подойдёт — сайту нужны Docker, Python и PostgreSQL. Достаточно 2 ГБ памяти, 1–2 ядер и 20–40 ГБ диска (у Hostinger — тарифы «VPS KVM»).

Что получится: Caddy принимает HTTPS на портах 80/443 и сам выпускает и продлевает сертификат Let's Encrypt → nginx (сайт и `/api`) → backend → PostgreSQL. Сервис `backup` раз в сутки сохраняет копию базы и файлов.

### 1. Домен

В панели, где куплен домен, создайте DNS-записи и подождите, пока они заработают (от нескольких минут до нескольких часов):

| Тип | Имя | Значение |
|---|---|---|
| A | `@` | IP-адрес VPS |
| A | `www` | IP-адрес VPS (необязательно: `www` будет перенаправлять на основной адрес) |

Проверка: `ping nexalanguage.com` должен показать IP сервера.

Для `nexalanguage.com` (DNS на Hostinger, на ноябрь 2026): запись `A @` сейчас ведёт на страницу-заглушку Hostinger (`2.57.91.91`) — замените её значение на IP VPS в hPanel → «Домены» → «DNS / Nameservers». `www` уже настроен как псевдоним основного домена, его трогать не нужно. Почтовых (MX) записей пока нет: для писем создайте ящик, например `no-reply@nexalanguage.com`, в Hostinger Email — MX и SPF-записи добавятся при подключении почты.

### 2. Сервер

Подключитесь по SSH (`ssh root@IP-сервера`) и выполните:

```bash
curl -fsSL https://get.docker.com | sh
```
```bash
git clone https://github.com/Wh1tetail/Nexa.git /opt/nexa && cd /opt/nexa
```

Если на сервере включён файрвол `ufw`, откройте SSH и веб-порты (8080 открывать не нужно):

```bash
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp && ufw allow 443/udp && ufw enable
```

### 3. Настройки (`.env`)

```bash
cp .env.production.example .env && nano .env
```

Обязательно заполните:

| Параметр | Значение |
|---|---|
| `DOMAIN` | `nexalanguage.com` (без `https://`) |
| `PUBLIC_URL` | `https://nexalanguage.com` — используется в ссылках из писем |
| `HTTP_BIND` | `127.0.0.1` — сайт снаружи доступен только через HTTPS |
| `POSTGRES_PASSWORD` | `python3 -c "import secrets; print(secrets.token_urlsafe(24))"` |
| `SECRET_KEY` | `python3 -c "import secrets; print(secrets.token_urlsafe(48))"` |

Почта (приглашения, восстановление пароля, копии уведомлений) — данные SMTP даёт почтовый сервис домена:

| Параметр | Пример |
|---|---|
| `EMAIL_BACKEND` | `smtp` |
| `EMAIL_FROM` | `NEXA <no-reply@nexalanguage.com>` |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` | адрес сервера, логин (обычно e-mail) и пароль ящика |
| `SMTP_PORT` | `587` (тогда `SMTP_STARTTLS=true`, `SMTP_SSL=false`) или `465` (тогда `SMTP_SSL=true`) |

`.env` хранит пароли: он не попадает в git, не отправляйте его никому.

### 4. Запуск

```bash
docker compose --profile https up -d --build
```

Первая сборка занимает несколько минут. Состояние: `docker compose ps` (все сервисы `running`/`healthy`), логи: `docker compose logs -f`. Через минуту после старта сайт открывается на `https://nexalanguage.com` с действующим сертификатом.

### 5. Первый администратор и проверка почты

```bash
docker compose exec backend python -m scripts.create_admin --email you@nexalanguage.com --name "Имя Фамилия"
```

Пароль спросят дважды (минимум 8 символов, буквы и цифры). Дальше администратор входит на сайт и создаёт преподавателей и учеников в интерфейсе. Если пароль администратора забыт — та же команда с `--reset-password`.

```bash
docker compose exec backend python -m scripts.send_test_email --to you@example.com
```

Команда отправит тестовое письмо и покажет ошибку SMTP, если что-то не так (обычные письма об ошибках не сообщают — только в лог).

**Не запускайте `scripts.seed` на рабочем сервере** — он создаёт демо-пользователей с общим паролем.

### Резервные копии

Сервис `backup` при старте и затем каждые `BACKUP_INTERVAL_HOURS` часов (по умолчанию 24) кладёт в `BACKUP_DIR` (по умолчанию `/opt/nexa/backups`) два файла: `db-ДАТА.dump` (база) и `files-ДАТА.tar.gz` (загруженные файлы). Копии старше `BACKUP_KEEP_DAYS` дней (по умолчанию 14) удаляются. Журнал: `docker compose logs backup`.

Копии лежат на том же сервере — периодически скачивайте их к себе, например:

```bash
scp -r root@IP-сервера:/opt/nexa/backups ./nexa-backups
```

Восстановление (заменяет текущие данные!):

```bash
docker compose stop backend backup
```
```bash
docker compose exec -T db pg_restore -U nexa -d nexa --clean --if-exists --no-owner < backups/db-ДАТА.dump
```
```bash
docker compose run --rm --no-deps -v "$PWD/backups:/backups" -u root --entrypoint sh backend -c "cd /app/storage && tar -xzf /backups/files-ДАТА.tar.gz && chown -R app:app ."
```
```bash
docker compose --profile https up -d
```

(`nexa` — значения `POSTGRES_USER` / `POSTGRES_DB` из `.env`.)

### Обновление сайта

```bash
cd /opt/nexa && git pull && docker compose --profile https up -d --build
```

Миграции базы применяются автоматически при старте backend; при перезапуске сервис `backup` сразу делает свежую копию.

### Что проверяется автоматически

CI на каждом коммите собирает весь стек в Docker и проверяет: сайт и API через nginx, вход, поток уведомлений, создание первого администратора, появление копии базы и файлов (и что дамп читается `pg_restore`), корректность конфигурации Caddy. Сам выпуск сертификата и отправку через настоящий SMTP проверить можно только на сервере с доменом.

## Что осталось / ограничения (честно)
- Казахские и английские тексты (интерфейс, ответы сервера, письма) переведены без носителя языка — их стоит вычитать.
- Старые уведомления, созданные до этапа 11, остаются на русском (тексты уведомлений сохраняются при создании).

- S3-хранилище реализовано (`STORAGE_BACKEND=s3`), но проверено только локальное.
- SMTP-отправка написана, но в этой среде проверялся только режим `console` — реального почтового сервера не было. На сервере проверьте её командой `scripts.send_test_email`.
- Выпуск HTTPS-сертификата (Caddy + Let's Encrypt) проверяется только на настоящем сервере с доменом: в CI проверяется лишь конфигурация.
- В чате нет редактирования и удаления сообщений, предпросмотра картинок и групповых чатов.
- Письма уведомлений только на русском (как и остальные письма школы) и проверены только в режиме `console`.
- Docker-образы и compose проверяются только в CI на GitHub: на этом компьютере Docker не установлен.
- Файлы при переводе ученика к другому преподавателю остаются привязаны к заданиям прежнего преподавателя (это ожидаемое поведение, но отдельного переноса истории нет).
